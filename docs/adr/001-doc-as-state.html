ADR 001 — Documents are the state

Status: accepted · foundational

Context

An orchestrator needs durable state: what's the plan, what's done, what's left, how to resume after an interruption. The classic answer is an explicit state machine — a task-state.json with an FSM, often driven by a background daemon. That machinery exists to compensate for an earlier era: small context windows (state had to be externalized) and weak agency (a process had to be told, step by step, what to do next).

Decision

OOD keeps no self-maintained JSON state machine. The durable state is the documents under docs/. Ephemeral coordination state (Agent Teams' task list) is owned by the harness and never hand-edited.

  • docs/plans is the program counter; docs/reports are the completion markers. Progress is readable as files.
  • The Agent Teams JSON is treated as disposable — the truth is the plan.

Consequences

easierharder / accepted
Human and AI can read state. Resume by re-reading docs. No FSM to build or keep consistent. Docs must be kept honest (the doc-sync skill). Gates rely on file/heading conventions rather than typed state.

Alternatives considered

  • task-state.json + FSM — rejected: ceremony that drifts from reality; redundant when 1M context + agency hold the work.
  • Background daemon — rejected: heavy; only pays off at breadth (many concurrent epics), which OOD does not target (see ADR 002).
